# Передача работы Claude Code: отдельный инструмент приёма заказов БАЗАРА

Дата состояния: 14 ноября 2026. Это инструкция для продолжения работы, а не подтверждение полной готовности.

## 1. Что владелец хочет сейчас

Оператор открывает отдельный адрес, входит и сразу оформляет заказ во время телефонного разговора. Ему не нужны витрина, навигация магазина и кабинет владельца. Последнее уточнение заменяет первоначальное требование добавить вкладку в кабинет.

Это отдельный интерфейс, **но общая система заказов**: единые createOrder, D1, остатки, цены, весовые правила, слоты, подтверждения, поставщики, сборщики, контролирующие, курьеры, Telegram, статистика и финансы. Источник сохраняется как PHONE_OPERATOR. Не создавать вторую базу, очередь, обработчик заказов или специальные карточки курьеров.

Владелец также хочет, чтобы телефонные заказы сохранились в истории покупателя, когда тот позже начнёт заказывать сам. В текущей системе клиентская база объединяет заказы по телефону, однако публичная история магазина хранит ключи заказов на устройстве. Автоматическая история покупательского аккаунта между устройствами **не реализована**. Нельзя обещать её без защищённой идентификации покупателя. Нельзя отдавать корзину или историю покупателю только по введённому номеру телефона.

Владелец явно попросил разместить инструмент на действующем сервере. Повторное согласие на саму эту публикацию не требуется. Проверяй конкретный target и доступы; покупка домена/платные сервисы не разрешались. Отдельный hostname пока не создан — сделан самостоятельный интерфейс `/operator.html`. Если нужен hostname, он должен вести к той же системе через безопасную маршрутизацию, а не к новой базе.

## 3. Карта реализации

### Самостоятельный интерфейс

- `public/operator.html`: отдельная страница, собственная шапка, выбор языка/города, desktop/mobile layout. Витрина и `public/app.js` здесь не загружаются.
- `public/operator.js`: bootstrap, обычный вход через `/api/login`, same-origin cookie, logout, загрузка каталога, контекст экрана. После создания заказа `complete(o)` показывает номер, поле результата разговора и кнопку существующего действия `confirm`. Поле причины обязательно. Новый заказ начинается здесь же.
- `public/phone-operator.js`: покупатель, каталог, корзина на одном экране, поиск по ru/hy/ka, редактирование граммов/количества/диапазонов, серверные quote и slots, черновики, повтор заказа из истории. Состояние в памяти `sessions`; `Сохранить` пишет в D1. Неопределённый ответ сети сохраняет точный `structuredClone` запроса и idem для повтора, блокируя изменение формы. При определённой серверной ошибке payload освобождается для исправления.
- `public/app.css`: стили трёх колонок и доступ к корзине на мобильном.
- `public/i18n.js`: новые строки на ru/hy/ka. Все последующие строки тоже переводить на три языка.
- `public/app.js`: первоначальная вкладка убрана из навигации; импорт и внутренний обработчик экрана остались. Это не основной вход оператора.

### Сервер

- `src/worker.mjs`: `/api/manage/phone/*` идёт через существующий парсер тела, сессию и CSRF, затем в `phoneAPI`.
- `src/phone-operator.mjs`: **пока только owner**, без доступа обычных сотрудников поставщиков.
  - `POST /api/manage/phone/create` → `createOrder(db,b,user)`.
  - `GET /api/manage/phone/customers?city_id=...&phone=...`: история авторизованному владельцу. Сейчас сравнение цифр номера, последние 1000 заказов города, максимум 20 совпадений. Просмотр аудитируется без записи самого номера в audit data.
  - `GET /api/manage/phone/drafts?city_id=...`: последние 30 черновиков текущего сотрудника в городе.
  - `POST /api/manage/phone/draft`: version guard и batch, сохранение + `operations_audit`.
- `src/commerce.mjs`: сигнатура `createOrder(db,b,operator=null)`. Доверенный контекст оператора передаётся сервером, публичный JSON не задаёт роль. Расчёты/резервирование и обычный номер BZ не дублируются. Для оператора `orders.source='PHONE_OPERATOR'`; CREATED получает actor сотрудника и источник. Используются обычные `orders`, `order_lines`, `order_groups`, `events`, `outbox`. Оплата остаётся UNPAID, confirmed=false до явного confirm.
- `migrations/0111_phone_operator.sql`: только таблица `phone_drafts` и индекс в существующей D1. Черновик не резервирует остатки/слот и не создаёт Telegram-события.
- `tests/phone-operator.test.mjs`: новые локальные интеграционные проверки.

Посмотреть также `src/customers.mjs`, `src/first-order.mjs`, `src/sources.mjs`, `src/security.mjs`, `src/order-hours.mjs`, `src/telegram.mjs`, `src/cloudflare.mjs`, `src/public-api.mjs` перед расширением этих частей.

## 5. Как запустить локально

```bash
npm ci
npm run dev
```

Открыть `http://localhost:5174/operator.html`. `tools/dev.mjs` сам применяет миграции и seed в локальную `.runtime/bazar.sqlite`. Локальные данные входа создаются в игнорируемом `.runtime/local-access.json`; используй их локально, не коммить и не выводи секреты в отчёты. Сервер не подключает Telegram. Не копируй этот локальный seed/SQLite в production.

Локальный старт не отключает часы работы глобально. За пределами часов тест оформления может закономерно получить ORDERS_CLOSED. Для отдельной проверки часов не ставь обходной env flag.

## 7. Незавершённые требования и известные риски

1. **Права операторов:** сейчас только owner. Нужны отдельные выдаваемые/отзываемые полномочия, проверяемые сервером и ограниченные городом при необходимости. Не раскрывай всю клиентскую базу поставщикам/курьерам через их обычные роли.
2. **Комбинированные режимы:** защищённая передача корзины покупателя оператору с согласием (Б) и ссылка покупателю на проверку/завершение черновика (В) отсутствуют. Номер телефона не является доказательством владения корзиной.
3. **Завтрашние заказы в любое время:** пока действуют обычные часы. Нет отложенного запуска. Обычный `action:confirm` сразу переводит в WEIGHING и разрешает дальнейшую обработку/курьерские уведомления. Текущая standalone кнопка вызывает именно его и не имеет защиты от раннего подтверждения будущей даты. **До использования для завтрашних заказов исправь это общим механизмом расписания, не просто обходом ORDER_HOURS.** Сохрани автора и результат разговора отдельно от времени запуска обработки. Изучи существующий cron/Telegram scheduling, не меняй алгоритмы отдельных поставщиков.
4. **Восстановление после создания:** запись результата звонка уже есть на странице результата, но после перезагрузки этот экран теряется. Нужен безопасный путь вернуться к созданному заказу в самостоятельном инструменте без кабинета.
5. **Черновики:** созданный заказ пока не закрывает/не архивирует его черновик. Один и тот же idem предотвращает дубликат, но нужно явно хранить результат/состояние завершения. Состояние до сохранения только в памяти страницы; не обещай автосохранение.
6. **Повторы/сеть:** проверь повтор после неизвестного HTTP ответа, обновление страницы, двойной клик и изменение данных. Подтверждение звонка использует свой command; после ошибки и редактирования причины тот же command может дать конфликт при уже выполненном действии. Нужен корректный recovery.
7. **История:** поиск ограничен 1000 заказов города/20 результатов; нормализация в phoneAPI — полные цифры, тогда как общая клиентская база использует phoneTail. Согласуй идентичность покупателя с общим кодом и индексами. Не вводи небезопасный поиск публичной истории по телефону.
8. **Интерфейс:** каталог показывает первые 100 совпадений; остальные находятся поиском. Проверь реальные объёмы, поиск hy/ka/ru, весовые режимы и доступные слоты, включая bulk lead и supplier delivery. Сервер эти ограничения проверяет, но экран не всегда заранее объясняет их. Нужны понятные переведённые ошибки (например VENDOR_CLOSED/BULK_TRANSFER_ONLY) и полный mobile flow.
9. **Аналитика:** источник сохраняется в обычной orders.source, но проверь отображение PHONE_OPERATOR в отчёте каналов. Вручную не меняй завершённые реальные заказы ради проверки.
10. **Приёмка исходного ТЗ:** не закрыта. PR остаётся Draft; не называй текущий код выполнением всех пунктов. Публикация отдельной текущей версии запрошена владельцем, но доступ к хостингу пока блокирует её.
