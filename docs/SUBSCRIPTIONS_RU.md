# «Забота о близких» — регулярные доставки (бэкенд)

## Статус

**Готово и проверено тестами (бэкенд-ядро):**
- расписание: по дням недели, каждые N дней, по числам месяца, по конкретным датам;
- программа с плательщиком, получателем, адресом, товарами, бюджетом и секретным ключом плательщика;
- расчёт каждой доставки через существующие `priceBasket()` и `deliveryFee()`, заказ — через существующий `createOrder()`;
- деньги программы: пополнение и возврат подтверждает только оператор;
- планировщик (cron уже запускается каждые 2 минуты, см. `wrangler.jsonc`), идемпотентный и устойчивый к сбоям;
- действия плательщика (пауза, пропуск, перенос, изменение графика/товаров/адреса, отмена, запрос пополнения и возврата, согласие на новую цену);
- отмена заказа программы не освобождает деньги сама: решение принимает оператор.

**Не готово — сайт пока НЕ может принимать такие программы от клиентов:**
- интерфейс «Забота о близких» (шесть шагов, витрина, кнопки на главной и в мобильном меню);
- личный кабинет плательщика (список программ, история, отчёты в интерфейсе);
- админ-раздел «Абонементы» (календарь, группировка, финансовые показатели в интерфейсе);
- трёхъязычные строки hy/ru/ka (в API сейчас только коды ошибок и русский текст в `name` товаров);
- уведомления: нигде ничего не отправляется; события пишутся в `subscription_events`, операторских задач пока нет;
- подтверждение получения и жалобы получателем (отдельного ключа у получателя нет, это намеренно);
- замены товаров: статус `WAITING_STOCK` есть, а процесса согласования замены — нет;
- фото вручения, отчёт плательщику по доставкам;
- проверка миграции `0099` и работы на настоящем Cloudflare D1 (здесь — SQLite-совместимый адаптер).

## Модель данных

- `subscription_programs` — программа: плательщик, получатель, адрес, зона, время, график (JSON), товары (JSON), лимит на одну доставку, версия, `planned_on`, хэш ключа плательщика, данные о согласии (`consent_by`: плательщик или оператор, `consent_note` — кто и когда дал согласие при оформлении по телефону).
- `subscription_deliveries` — доставка на день. `UNIQUE(program_id, day)`: на один день программы не может быть двух доставок. `allocated_minor` — деньги, выделенные этой доставке. `order_id UNIQUE` — один заказ на доставку.
- `subscription_funds` — движение денег программы: `PAYMENT` (пополнение) и `REFUND` (возврат), статусы `PENDING` → `CONFIRMED` / `REJECTED`.
- `subscription_events` — история изменений и действий системы.

Все суммы — целые тетри, вес — граммы (как в остальном проекте).

## Правила денег

1. Программа не создаёт заказов, пока оператор не подтвердил пополнение. Подтверждение клиента или его сообщение оплатой не считается.
2. Перед созданием заказа доставка получает `allocated_minor` условным `UPDATE`: одновременно выделить одни и те же деньги дважды нельзя.
3. Инвариант: **занято = сумма `allocated_minor` по доставкам программы**. Деньги освобождаются только при пропуске или переносе до создания заказа, при отмене программы до заказов и решением оператора.
4. Заказ программы оплачивается из её средств сразу при создании (`payments.command = 'sub-pay-<id>'`, уникален). Поэтому курьер не получает неоплаченный заказ.
5. Отмена созданного заказа: доставка → `FAILED` (`ORDER_CANCELLED`), деньги **остаются занятыми**. Оператор через `manage/subscriptions/resolve` выбирает:
   - `RETURN_TO_BALANCE` — деньги возвращаются в остаток программы;
   - `REFUND` — создаётся ожидающий возврат, который уходит в доступный остаток только после выплаты и подтверждения оператором.
   Заказ при этом получает обычный статус `REFUND_REVIEW`, который видит оператор в существующем разделе заказов. **Внимание:** существующая отметка `REFUND_REVIEW` не знает о программе. Чтобы не вернуть деньги дважды, оператор обязан сверяться с ожидающими возвратами программы и не выплачивать по заказу отдельно.
6. Остаток для плательщика: `оплачено − подтверждённые возвраты − ожидающие возвраты − занято`. Ожидающий возврат не предлагается второй раз.
7. Возврат подтверждает оператор и только после фактической выплаты. Автоматических списаний и платёжных шлюзов нет.

## Планировщик

- Запуск: cron `*/2 * * * *` из `wrangler.jsonc`; функция `runSubscriptionPlanner`.
- Раз в сутки на программу достраивается план на 120 дней (`planned_on`). План не резервирует товар.
- Заказ создаётся за **2 дня** до доставки (`ORDER_LEAD_DAYS`). Так скоропортящиеся товары не резервируются вперёд, а при создании заказа доставка для плательщика блокируется (`DELIVERY_LOCKED`).
- Порядок для каждой доставки: уже есть заказ (восстановление после сбоя) → котировка → проверка бюджета (`WAITING_APPROVAL`) → свободный слот (`WAITING_SLOT`) → выделение денег (`WAITING_FUNDS`) → `createOrder` → оплата → статус `ORDERED`.
- Ошибки `createOrder` делятся на три группы: повторить позже (`PLANNED`), товар недоступен (`WAITING_STOCK`), минимальная сумма (`WAITING_CHANGE`). Остальные — `FAILED`, то есть ручная обработка.
- Зависшая заявка (`CLAIMED` дольше 10 минут) возвращается в план. Если заказ уже был создан, он находится по ключу `idem = sub-<id>` и привязывается без дубля.
- Неизвестные ошибки логируются (`console.error`) и не меняют состояние доставки.

Проверено тестами: повторный запуск, три параллельных запуска, сбой после создания заказа, сбой до него, нехватка денег, частичное пополнение, занятый слот, превышение бюджета, пауза и возобновление.

## Расхождения ТЗ и кода — нужно решение владельца

1. **Бесплатная доставка в села от 160 ₾.** В `src/zones.mjs` у всех сёл `free_from: 16000`. ТЗ говорит «доставка в сёла остаётся платной» и «от 100 ₾ для сёл не действует». Код соответствует запискам владельца от 07.11 в комментариях, но это противоречит тексту ТЗ. Я ничего не менял.
2. **Минимум 30 ₾ для Ахалкалаки не действует для обычных заказов.** В коде минимальной суммы заказа нет: единственный «минимум» относится к весу товара. Для программ я ввёл минимум (`MIN_ORDER`), иначе они нарушили бы условие ТЗ. Для обычных заказов поведение не менял: это изменило бы существующую корзину. Нужно подтверждение владельца.
3. **«1 Городок»**: минимума ТЗ не задаёт. Сейчас минимума нет; для программ это тоже открытый вопрос.
4. **Тарифы на свежей базе.** Миграция `0094` выставляет порог бесплатной доставки 100 ₾ через `UPDATE cities`, но город создаёт `seed` уже после миграций. В тестовой базе `free_delivery_from` оказался `NULL`, то есть бесплатная доставка не работала бы. Рабочая база тарифы получила раньше, поэтому сайт сейчас в порядке; копия на новом D1 получит неверные тарифы. В тестах тариф выставлен явно. Исправление seed — отдельная задача, я её не делал.
5. **Адрес публикации.** ТЗ: `bazar.xugushik.workers.dev`. В `wrangler.jsonc`: `bazar-demo.xugushik.workers.dev`. `AGENTS.md` требует ветку `feature/bazar-store`. Публикацию не выполнял.
6. **Версия Node.** `package.json` требует Node 24, в песочнице Node 22.23. Все тесты проходят на 22; перед публикацией нужен прогон на 24.
7. **Первый заказ бесплатно.** `createOrder` убирает доставку для первого заказа, если `cities.first_order_free = 1`. Сейчас флаг выключен. Если его включить, первая доставка программы тоже станет бесплатной. Нужно решить, нужно ли это.

## Ограничения и риски

- Замены товаров и согласование замены не реализованы.
- Изменение веса после сборки идёт по существующей логике заказа; как это ведёт себя с деньгами программы, отдельно не проверено.
- Изменение цены товара после заказа не пересчитывает уже созданный заказ (как и для обычных заказов).
- План строится на 120 дней, но всё, что создано, остаётся в таблицах: удаления нет.
- При росте числа программ ежедневное достраивание плана станет заметной нагрузкой на D1; нужен мониторинг.
- Ошибки планировщика видны только в логах Cloudflare; оповещения нет.
- Гонки между планировщиком и оператором защищены условными `UPDATE` и версиями программы, но окончательная проверка — только на настоящем D1.
